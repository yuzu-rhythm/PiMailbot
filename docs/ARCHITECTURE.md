# アーキテクチャ

## モジュール

| モジュール | 責務 |
| --- | --- |
| `gmail_client.py` | OAuth更新、Gmail REST通信、限定したメール操作 |
| `gmail_accounts.py` | 設定マニフェストの検証、アカウント照合、操作の振り分け |
| `gmail_sync.py` | 差分履歴カーソル、通知、処理・監査記録、削除待ちキュー |
| `gmail_notifier.py` | 通知ループ、Todoist登録確認後の保管 |
| `mail_categories.py` | 内容の複数選択、保存前比較、分類と保管 |
| `mail_triage.py` | 処理分類、変更前状態の保存、取り消し |
| `mail_history.py` | 短い履歴、直後の取り消し、通知削除・再表示 |
| `todoist_sync.py` | ローカルタスクとTodoistの任意連携 |
| `dashboard.py` | 外部サービスの読み取りと安全なスナップショット |
| `dashboard_static/` | 日本語表示、日単位・週間予定、未処理の強調 |
| `storage.py` | タスク、手動クレジット、画像メタデータのSQLite保存 |

## アカウントと処理単位

通知DBとOAuthはアカウントごとに分離します。GmailメッセージIDはDB内で一意、Discord通知IDはサーバー・チャンネルと対応付けます。メール取得の履歴では `messageAdded` を対象とし、ラベルの変更だけを新着として扱いません。既存IDは挿入時にも重複を防ぎます。

ただし、Discordへ投稿してからDBへ投稿済みと記録するまでの停止は、完全には単一トランザクションにできません。この区間の重複通知は既知の制約です。

## 分類して保管

1. 許可ユーザー・サーバー・チャンネルと保存済み通知を照合する。
2. アカウントの操作ロックを取得し、内容分類の現在値と選択画面を開いた時点を比較する。
3. 変更前ラベル・管理対象ラベルID・分類の選択を処理記録へ保存する。
4. Gmailのmodifyで内容分類・処理済みラベル・受信トレイからの除去をまとめて実行する。
5. 保存内容と保管を読み取り確認し、完了を記録する。
6. 元通知の削除をキューへ入れ、Bot本人の投稿だけを削除する。

削除失敗時は通知削除のみ再試行します。既読・スターや無関係なラベルは変更しません。10分間の取り消しボタンには分類世代を結び付け、古い画面から後の操作を取り消さないようにします。取り消しは管理対象だけを復元します。

## 外部連携と限界

Todoistは作成済み確認とGmail保管を分けます。Undo後も作成済みTodoistタスクは残します。Geminiは任意で、現在の複数アカウント経路では実メールの自動AI送信を無効にしています。

ダッシュボードは読み取り専用で127.0.0.1に限定し、HTTP Host検査、固定配信ファイル、CSPを使用します。通信失敗時は前回の値と更新失敗を表示します。外部から利用できる認証付きサービスとしては設計・検証していません。

Gmail上で他クライアントも同時にラベルを変更できるため、保存前比較で完全な排他性を保証することはできません。SQLiteのトランザクションもGmail・Discordへはまたがりません。
